# Kaiten Voice Control
## Спецификация MVP v0.1

**Дата:** 13.08.2026  
**Статус:** исходная спецификация проекта

---

## 1. Назначение

Kaiten Voice Control — диалоговый клиент для управления Kaiten через мессенджер MAX.

Основная задача системы — убрать рутинные действия по наполнению и администрированию досок Kaiten и заменить их:

- текстовыми сообщениями на естественном языке;
- голосовыми сообщениями;
- прямыми командами без использования ИИ;
- отправкой фотографий непосредственно в диалог с ботом.

Система не является автономным AI-менеджером проекта.

Все изменения состояния Kaiten выполняются только по явному запросу пользователя.

Исключение — фоновый контроль сроков: система может самостоятельно читать карточки Kaiten и отправлять пользователю уведомления о срочных и просроченных карточках, но не изменяет их.

---

# 2. Базовые принципы

## 2.1. Kaiten — источник состояния проекта

Kaiten является единственным источником истины для:

- пространств;
- досок;
- колонок;
- карточек;
- комментариев;
- сроков;
- вложений;
- текущего положения карточек.

Собственная БД сервиса не дублирует содержимое Kaiten.

---

## 2.2. MAX — основной пользовательский интерфейс

Все пользовательское взаимодействие выполняется через MAX.

Поддерживаемые типы входа:

1. текст;
2. голосовое сообщение;
3. фотография;
4. slash-команда;
5. ответы на уточняющие вопросы бота;
6. нажатия inline-кнопок.

Отдельный пользовательский web-интерфейс в MVP не требуется.

---

## 2.3. Два режима управления

Система предоставляет два равноправных интерфейса к одному и тому же командному ядру.

### Детерминированный режим

Команды выполняются без LLM.

Пример:

```text
/due 008-08 20.08.2026
```

### Диалоговый режим

Пользователь сообщает то же самое естественным языком:

```text
Поставь 008-08 срок до двадцатого августа.
```

или голосом.

LLM используется только для определения намерения и параметров операции.

Результатом обоих способов должна стать одна внутренняя команда:

```text
SetDueDate(
    card="008-08",
    date="2026-08-20"
)
```

# 4. Обязательные операции MVP

## 4.1. Работа с досками

### `boards.list`

Получить список доступных пользователю досок.

Примеры:

```text
/boards
```

```text
Какие у меня есть доски?
```

Выбрать рабочую доску для последующих команд.

Пример:

```text
/use LineBuilder
```

```text

```

Выбранная доска сохраняется в контексте пользователя.

# 5. Работа с карточками

## 5.1. Получить все карточки

### `cards.list`

Прямая команда:

```text
/cards
```

Диалог:

```text
Покажи все карточки.
```

Если карточек много, используется пагинация.

Бот выводит:

- номер в текущем списке;
- название;
- колонку;
- срок, если задан.

Пример:

```text
Карточки 1–10 из 37

1. 008-08 — Ручная приёмка
2. 009-00 — Аудит ядра
3. 009-01 — Модель данных
...
```

---

## 5.2. Получить карточки конкретной колонки

### `cards.list_by_column`

Прямая команда:

```text
/column "Ручная приёмка"
```

Диалог:

```text
Покажи карточки в ручной приёмке.
```

Допускаются разговорные варианты названия колонки.

Resolver должен сопоставить пользовательское название с реальной колонкой Kaiten.

---

## 5.3. Получить карточку

### `card.get`

Прямая команда:

```text
/card 008-08
```

Диалог:

```text
Покажи 008-08.
```

Возвращаются как минимум:

- название;
- описание;
- текущая колонка;
- срок;
- наличие вложений;
- количество комментариев.

После успешного открытия карточка становится `current_card`.

---

## 5.4. Создать карточку

### `card.create`

Прямая команда:

```text
/new 009-01 Аудит API
```

Диалог:

```text
Создай карточку 009-01 «Аудит API».
```

Для MVP обязательно:

- название;
- рабочая доска;
- целевая колонка по умолчанию либо указанная пользователем.

---

## 5.5. Переместить карточку

### `card.move`

Прямая команда:

```text
/move 008-08 "Завершено"
```

Диалоговые варианты:

```text
Перенеси 008-08 в завершённые.
```

```text
008-08 готова.
```

```text
Карточку автоматической приёмки можно закрывать.
```

Resolver должен определить:

1. карточку;
2. целевую колонку.

После операции состояние проверяется повторным чтением карточки.

---

# 6. Комментарии

## 6.1. Добавить комментарий

### `comment.add`

Прямая команда:

```text
/comment 008-08 Ручная проверка пройдена, замечаний нет.
```

Диалог:

```text
Добавь в 008-08 комментарий, что ручная проверка пройдена и замечаний нет.
```

При наличии `current_card` допускается:

```text
Добавь комментарий, что всё проверено.
```

LLM может нормализовать разговорную формулировку, но не должна добавлять факты, отсутствующие в исходном сообщении пользователя.

---

# 7. Управление сроками

Внутренняя модель содержит две операции:

```text
SetDueDate
ClearDueDate
```

Отдельной операции «изменить срок» не требуется: повторный `SetDueDate` заменяет существующий срок.

---

## 7.1. Добавить срок

Прямая команда:

```text
/due 008-08 20.08.2026
```

Диалог:

```text
Поставь 008-08 срок до двадцатого августа.
```

---

## 7.2. Изменить срок

```text
Перенеси срок 008-08 на следующий понедельник.
```

Используется `SetDueDate`.

---

## 7.3. Убрать срок

Прямая команда:

```text
/nodue 008-08
```

Диалог:

```text
Убери срок у 008-08.
```

---

## 7.4. Интерпретация дат

Поддерживаются:

- конкретные даты;
- сегодня;
- завтра;
- послезавтра;
- пятница;
- следующий понедельник;
- через три дня;
- до конца недели.

Если время явно не указано, операция трактуется как срок по календарной дате без конкретного времени.

## 8.2. Показать фотографии карточки

### `card.list_photos`

Прямая команда:

```text
/photos 008-08
```

Диалог:

```text
Покажи фотографии 008-08.
```

Алгоритм:

```text

 ↓
```

## 8.3. Анализ изображений

Автоматический анализ содержания фотографий не входит в MVP.

Фото:

- прикрепляются;
- извлекаются;
- показываются пользователю.

Мультимодальное AI-распознавание рассматривается как возможное последующее расширение.

# 9. Summary карточки

### `card.summary`

Прямая команда:

```text
/summary 008-08
```

Диалог:

```text
Сделай суммари по 008-08.
```

или:

```text
Кратко скажи, что сейчас с этой карточкой.
```

Система получает:

- название;
- описание;
- текущую колонку;
- срок;
- комментарии карточки;
- авторов и хронологию комментариев.

После этого LLM формирует краткую сводку.

Рекомендуемая структура ответа:

```text
008-08 — краткое состояние

Что сделано
- ...

Текущее состояние
- ...

Открытые вопросы
- ...

Краткий вывод
- ...
```

Summary должно:

- отражать только данные карточки;
- учитывать хронологию комментариев;
- отделять выполненное от открытых вопросов;
- не придумывать отсутствующие факты;
- быть значительно короче исходной истории.

# 10. Контекст диалога

Контекст является обязательной частью MVP.

Для каждого пользователя хранится отдельная диалоговая сессия.

Минимальный контекст:

```text
current_board
current_card
previous_user_message
previous_bot_message
last_card_list
pending_command
```

---

## 10.1. Контекст текущей карточки

Пример:

```text
Покажи 008-08.
```

После этого:

```text
Поставь ей срок на пятницу.
```

Слово `ей` разрешается через:

```text
current_card = 008-08
```

---

## 10.2. Контекст предыдущего сообщения

Предыдущая пользовательская реплика должна сохраняться как минимум до успешного завершения следующей операции.

Это необходимо для уточняющих диалогов.

---

# 11. Pending Command

Если команда понятна, но объект не найден либо найден неоднозначно, исходная команда не должна теряться.

Создаётся `PendingCommand`.

Пример исходного сообщения:

```text
Добавь в карточку по API комментарий, что проверка пройдена.
```

Поиск вернул:

```text
008-03 API audit
009-01 Kaiten API audit
012-04 API documentation
```

В состоянии диалога сохраняется:

```json
{
  "intent": "comment.add",
  "original_message": "Добавь в карточку по API комментарий, что проверка пройдена.",
  "arguments": {
    "comment": "Проверка пройдена."
  },
  "unresolved_entity": {
    "type": "card",
    "query": "карточка по API"
  },
  "candidates": [
    "008-03",
    "009-01",
    "012-04"
  ]
}
```

Бот отвечает:

```text
Нашёл три подходящие карточки:

1. 008-03 API audit
2. 009-01 Kaiten API audit
3. 012-04 API documentation

Какую выбрать?
```

Ответ:

```text
Вторую.
```

должен продолжать исходную команду, а не интерпретироваться как новая самостоятельная задача.

---

## 11.1. Многошаговое уточнение

Допускается несколько последовательных уточнений.

Пример:

```text
Поставь карточке про API срок на пятницу.
```

Бот:

```text
Нашёл три подходящие карточки. Какую выбрать?
```

Пользователь:

```text
Ту, которая в работе.
```

После фильтрации остаются две.

Бот:

```text
В работе две карточки:

1. 008-03
2. 009-01

Какую выбрать?
```

Пользователь:

```text
009-01.
```

Только после этого выполняется исходный `SetDueDate`.

---

## 11.2. Состояния PendingCommand

```text
RECEIVED
 ↓
PARSED
 ↓
RESOLVING
 ↓
NEEDS_CLARIFICATION
 ↓
READY
 ↓
EXECUTED
```

Команда может несколько раз переходить между:

```text
RESOLVING
↕
NEEDS_CLARIFICATION
```

# 12. Уведомления

Уведомления являются обязательной частью MVP.

Использование Kaiten webhooks не требуется.

Сервер самостоятельно выполняет периодический polling Kaiten API.

---

## 12.1. Принцип

```text
Scheduler
 ↓
Kaiten Adapter
 ↓
получение карточек со сроками
 ↓
Notification Policy
 ↓
Deduplication
 ↓
MAX
 ↓
Пользователь
```

---

## 12.2. Команды

### Включить уведомления

```text
/notify on
```

или:

```text
Включи уведомления.
```

### Выключить

```text
/notify off
```

### Показать состояние

```text
/notify status
```

---

## 12.3. Какие карточки контролируются

Учитываются как минимум:

- карточки, срок которых приближается;
- карточки со сроком сегодня;
- просроченные карточки.

Порог предварительного предупреждения должен храниться в пользовательских настройках.

Рекомендуемый первоначальный вариант:

```text
за 1 день;
в день срока;
после наступления просрочки.
```

В дальнейшем пользовательская политика может быть расширена.

---

## 12.4. Защита от повторных уведомлений

Система не должна отправлять одинаковое сообщение при каждом цикле polling.

Хранится история уведомлений:

```text
user_id
card_id
due_date
notification_type
sent_at
```

Типы событий:

```text
DUE_SOON
DUE_TODAY
OVERDUE
```

При изменении срока карточки старое состояние уведомлений для предыдущего срока не должно препятствовать отправке уведомлений по новому сроку.

---

## 12.5. Ограничение автономности

Фоновый механизм имеет только право:

```text
READ Kaiten
SEND MAX notification
```

Он не имеет права:

```text
CREATE card
MOVE card
CHANGE due date
ADD comment
DELETE
ARCHIVE
```

без пользовательской команды.

# 15. Голосовой режим

Голос является полноценным входным интерфейсом, а не отдельным набором команд.

Pipeline:

```text
MAX voice
 ↓
получение audio
 ↓
Speech-to-Text
 ↓
полученный текст
 ↓
тот же LLM Interpreter,
что используется для обычных сообщений
```

После транскрибации голосовая и текстовая команда обрабатываются одинаково.

Speech-to-Text должен быть реализован через абстракцию провайдера, чтобы конкретный сервис распознавания речи можно было заменить без изменения бизнес-логики.

---

# 16. Пользовательская модель

Система проектируется как multi-user даже в первоначальном личном прототипе.

Основная связь:

```text
User
 ├── MAX identity
 ├── Kaiten connection
 ├── current dialog session
 ├── preferences
 └── notification settings
```

Каждый пользователь подключает собственную учётную запись Kaiten.

---

# 17. Собственные данные сервиса

Минимальная собственная БД должна содержать сервисные данные.

Рекомендуемые сущности:

```text
users
kaiten_connections
max_chats
dialog_sessions
pending_commands
notification_settings
notification_history
```

Содержимое карточек Kaiten в собственную БД постоянно не копируется.

---

# 18. Безопасность

Обязательно:

- Kaiten API token хранится зашифрованным;
- данные разных пользователей изолированы;
- MAX user/chat связывается с конкретным пользователем сервиса;
- пользователь может работать только со своим Kaiten connection;
- секреты не выводятся в логи;
- операции логируются без сохранения чувствительных токенов.

---

# 19. Поведение при ошибках

## Карточка не найдена

Не выполнять операцию.

Ответить:

```text
Не нашёл карточку «...».
Уточни название или номер.
```

При этом сохранить `PendingCommand`.

---

## Найдено несколько карточек

Не выбирать карточку произвольно.

Показать кандидатов и запросить уточнение.

---

## Колонка не найдена

Показать доступные близкие варианты.

---

## Kaiten API недоступен

Не сообщать об успешном выполнении операции.

Ответ:

```text
Не удалось выполнить команду: Kaiten сейчас недоступен.
Изменения не внесены.
```

---

## LLM не смогла уверенно распознать намерение

Не выполнять предположительное изменение.

Задать краткий уточняющий вопрос.

---

# 20. Что не входит в MVP

Не реализовывать на первом этапе:

- Kaiten webhooks;
- автономное управление проектом;
- автоматическое перемещение карточек;
- автоматическое создание карточек без команды;
- lifecycle engine;
- анализ состояния всего проекта;
- автоматическое планирование работ;
- автоматизации Kaiten;
- MCP как обязательную часть;
- анализ содержания фотографий;
- отдельный полноценный web-UI;
- сложную отчётность;
- синхронизацию собственной копии Kaiten.

---

# 21. Инвариант системы

Главное правило:

> Любое изменение данных Kaiten выполняется только как следствие явной команды пользователя.

Единственная разрешённая фоновая активность:

> периодическое чтение сроков и отправка уведомлений в MAX.

---

# 22. Критерии приёмки MVP

MVP считается функционально завершённым, если пользователь может через MAX:

1. подключить свой Kaiten;
2. выбрать рабочую доску;
3. получить список всех карточек;
4. получить список карточек конкретной колонки;
5. открыть карточку;
6. создать карточку;
7. переместить карточку;
8. добавить комментарий;
9. добавить срок;
10. изменить срок;
11. убрать срок;
12. отправить фото и приложить его к карточке;
13. получить прикреплённые фотографии;
14. получить AI-summary карточки и её комментариев;
15. выполнять перечисленные операции slash-командами без LLM;
16. выполнять те же операции естественным текстом;
17. выполнять те же операции голосом;
18. продолжать диалог относительно текущей карточки без повторения её идентификатора;
19. проходить многошаговое уточнение при неоднозначном поиске;
20. не терять исходную команду во время уточнения;
21. включать и отключать уведомления;
22. получать уведомления о приближающихся и просроченных сроках;
23. не получать дублирующиеся уведомления при каждом цикле polling.

---

# 23. Возможное развитие после MVP

Не является частью текущей реализации, но архитектура не должна препятствовать:

- коммерческому доступу;
- тарифам сервиса;
- подключению нескольких Kaiten-пространств;
- поддержке других task tracker через адаптеры;
- дополнительным мессенджерам;
- анализу фотографий;
- более сложным политикам уведомлений;
- работе с файлами других типов;
- расширенной работе с чек-листами;
- batch-командам;
- дополнительным AI-summary и поиску по истории карточек.

# 24. Целевая формулировка продукта

**Kaiten Voice Control — диалоговый клиент Kaiten в MAX, позволяющий управлять досками, карточками, комментариями, сроками и вложениями с помощью текста, голоса и прямых команд, с сохранением контекста диалога и контролем приближающихся сроков.**
