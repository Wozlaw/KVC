# 002-00a - Final MVP service data model specification

## Executive summary

This document freezes the MVP service data model for Kaiten Voice Control branch `002`.

The first business schema contains exactly seven KVC-owned tables:

```text
users
max_chats
kaiten_connections
dialog_sessions
pending_commands
notification_settings
notification_history
```

KVC does not store a permanent local copy of Kaiten boards, columns, cards, comments, due dates, attachments, card position, or card state. KVC stores only internal user identity, external references, user configuration, encrypted Kaiten access, bounded restart-safe dialog context, pending command workflow state, and notification dedup/delivery state.

This stage is specification-only. No SQLAlchemy models, Alembic revision, repository layer, business logic, DDL, seed data, or integration code is created here.

Final status: `ACCEPTED SPECIFICATION - READY FOR 002-01`.

## Accepted architectural decisions

The following decisions from `002-00` are accepted and fixed for MVP implementation:

| Decision | Final value | Consequence |
|---|---|---|
| Internal PK type | `UUID` | UUIDs are generated by application code; no PostgreSQL UUID extension is required just for ID generation |
| MAX scope | `PRIVATE` 1:1 chat only | Group chat support is out of MVP and must be rejected or ignored at application boundary |
| Kaiten connections | One KVC user has one Kaiten connection | Enforced by `UNIQUE (user_id)` on `kaiten_connections` |
| Pending command terminal states | `FAILED`, `CANCELLED`, `EXPIRED` included | Failed, cancelled, and stale commands are explicit terminal rows |
| Notification delivery state | `RESERVED`, `SENT`, `FAILED` | Enables minimal reservation/dedup semantics without a full outbox |
| Timezone default | `UTC` | User notification dates are deployment-neutral and not tied to server timezone |
| User deletion | No physical user deletion in MVP | Users are disabled through `users.status`; no `deleted_at` |

Two implementation clarifications are also fixed:

- The internal FK from `dialog_sessions` to `max_chats` is named `max_chat_binding_id`. The name `max_chat_id` is reserved for the external MAX chat identifier stored in `max_chats.max_chat_id`.
- Secondary indexes must not duplicate identical `UNIQUE` or partial `UNIQUE` indexes unless a separate query pattern proves the need.

## Data ownership boundary

| Data | Source of truth | Stored in KVC DB | Storage format | Reason |
|---|---|---:|---|---|
| Kaiten spaces | Kaiten | No | Not stored | KVC must not mirror Kaiten project structure |
| Kaiten boards | Kaiten | Transient reference only | `TEXT` external ID plus optional display snapshot | Current board context |
| Kaiten columns | Kaiten | Transient candidate only | JSONB resolver/list snapshot | Clarification and display only |
| Kaiten cards | Kaiten | Transient reference/dedup marker only | `TEXT` external ID in context, candidates, notification history | Context and dedup |
| Kaiten card descriptions | Kaiten | No | Not stored | Read live for card display/summary |
| Kaiten comments | Kaiten | No | Not stored | Read live for card display/summary |
| Kaiten due dates | Kaiten | Dedup marker only | `DATE` in notification history | Due date participates in notification uniqueness |
| Kaiten attachments | Kaiten | No | Not stored | Files are handled through Kaiten/MAX integrations |
| Current board | KVC dialog context | Yes | `current_board_id`, `current_board_name` | Restart-safe command context |
| Current card | KVC dialog context | Yes | `current_card_id`, `current_card_title` | Pronoun and implicit-command context |
| MAX identity | MAX | Yes | `TEXT` external IDs | Incoming routing and notification destination |
| User Kaiten token | User/Kaiten | Yes, encrypted only | `encrypted_api_token`, `token_encryption_version` | Per-user Kaiten access |
| PendingCommand | KVC | Yes | Row plus versioned JSONB payloads | Multi-step clarification and safe continuation |
| Notification settings | KVC | Yes | Boolean, threshold, timezone | User preferences |
| Notification history | KVC | Yes | Dedup key plus delivery state | Prevent duplicate polling notifications |
| Global app secrets | Environment/secret storage | No | Not stored | Provider/bot/infrastructure secrets |

JSONB fields must not become a hidden local Kaiten cache. They are bounded, versioned, temporary snapshots for dialog and resolver workflows.

## PendingCommand state machine

Active states:

```text
RECEIVED
PARSED
RESOLVING
NEEDS_CLARIFICATION
READY
```

Terminal states:

```text
EXECUTED
FAILED
CANCELLED
EXPIRED
```

Allowed transitions:

| From | To | Condition | Terminal target |
|---|---|---|---:|
| `RECEIVED` | `PARSED` | Parser or LLM produced an intent and initial arguments | No |
| `PARSED` | `RESOLVING` | Resolver starts external reference resolution | No |
| `RESOLVING` | `NEEDS_CLARIFICATION` | Resolver has zero or multiple candidates and needs user input | No |
| `NEEDS_CLARIFICATION` | `RESOLVING` | User reply is accepted as clarification | No |
| `RESOLVING` | `READY` | Required entities and arguments are resolved | No |
| `READY` | `EXECUTED` | Kaiten command completed successfully after explicit user command | Yes |
| active state | `CANCELLED` | User cancels or starts an incompatible new command | Yes |
| active state | `EXPIRED` | `expires_at` passes before completion | Yes |
| active state | `FAILED` | Parser/resolver/application/Kaiten/MAX failure prevents safe completion | Yes |

Clarification handling:

- A clarification reply must lock and re-read the active pending command.
- If the command is terminal, the reply must not mutate it.
- If state is `NEEDS_CLARIFICATION`, increment `clarification_attempts`, update `unresolved_entity` and `candidates` as needed, then transition to `RESOLVING` or remain in `NEEDS_CLARIFICATION` through a new resolver cycle.
- `clarification_attempts` starts at `0` and must never be negative.

TTL semantics:

- `expires_at` is nullable for commands without an assigned TTL, but MVP should set it for unresolved/clarification flows.
- Expiration changes active state to `EXPIRED`; terminal rows are not active and do not block the partial unique index.

Execution/failure timestamps:

- `executed_at` is set only for `EXECUTED`.
- `FAILED`, `CANCELLED`, and `EXPIRED` do not set `executed_at`; their terminal reason is carried by `failure_reason` when useful and safe.

External Kaiten failure:

- If Kaiten is unavailable or rejects an operation, KVC must not claim success.
- The pending command transitions to `FAILED` unless a future retry design explicitly keeps it active.

## Dialog context contract

One active dialog session per user is enforced by:

```text
UNIQUE (user_id) WHERE ended_at IS NULL
```

The session is restart-safe but bounded:

- it is not a transcript;
- previous message fields are overwritten as dialog advances;
- `last_card_list` is overwritten by the next list/candidate response;
- `current_board_*` and `current_card_*` are context pointers/snapshots only;
- `expires_at` marks stale context;
- `ended_at` removes the row from the active-session unique predicate.

The internal MAX binding FK is `max_chat_binding_id`. The external MAX chat ID remains only `max_chats.max_chat_id`.

No separate `last_card_list_items` table is created in MVP.

## JSONB contracts

All JSONB payloads are application-contract payloads with `version = 1`. They are not normalized domain tables and are not a local Kaiten cache.

### `dialog_sessions.last_card_list`

Required fields:

```json
{
  "version": 1,
  "source": "cards.list",
  "generated_at": "2026-08-13T00:00:00Z",
  "items": []
}
```

Allowed `source` values are application-level strings such as:

```text
cards.list
cards.list_by_column
resolver.candidates
```

Each `items[]` element:

```json

  "ordinal": 1,
  "entity_type": "card",
  "external_id": "kaiten-card-id",
  "display_code": "008-08",
  "title": "short display snapshot",
  "column_name": "optional display snapshot",
  "due_date": "2026-08-20"
}
```

Required: `ordinal`, `entity_type`, `external_id`.

Optional: `display_code`, `title`, `column_name`, `due_date`.

`due_date` is a display/dedup-friendly snapshot only; Kaiten remains source of truth.

Default:

```json
{
  "version": 1,
  "payload": {}
}
```

`payload` is intent-specific. Examples:

```json
{
  "version": 1,
  "payload": {
    "card_id": "kaiten-card-id",
    "comment": "Проверка пройдена.",
    "due_date": "2026-08-20"

```

Required: `version`, `payload`.

Optional inside `payload`: command-dependent scalar arguments and external references.

### `pending_commands.unresolved_entity`

Shape:

```json
{
  "version": 1,
  "type": "card",
  "query": "карточка по API",
  "required_for": "card_id"
}
```

Required when present: `version`, `type`, `query`, `required_for`.

Allowed `type` values are application-level strings such as `card`, `board`, `column`.

Shape:

```json
{
  "version": 1,
  "items": [
    {
      "ordinal": 1,
      "entity_type": "card",
      "external_id": "kaiten-card-id",
      "display": "008-03 API audit",
      "metadata": {
        "column_name": "В работе"
      }
    }

```

Required: `version`, `items`.

Required per item: `ordinal`, `entity_type`, `external_id`, `display`.

Optional per item: `metadata`.

No JSONB GIN indexes are created because no accepted MVP query filters by nested JSONB fields.

## Secret storage contract

Not stored in PostgreSQL:

```text
PostgreSQL password
MAX bot token
MAX webhook secret
GigaChat credentials
SaluteSpeech credentials
token encryption key
.env contents
```

Stored in PostgreSQL:

```text
kaiten_connections.encrypted_api_token
kaiten_connections.token_encryption_version
```

Requirements:

- plaintext Kaiten token is never persisted;
- plaintext Kaiten token is not logged;
- plaintext Kaiten token is excluded from `repr`;
- plaintext Kaiten token is not included in migrations;
- plaintext Kaiten token is not included in reports;
- real token is not used in test fixtures;
- encryption key comes from environment or external secret storage;
- encryption key is never stored in PostgreSQL;
- `token_encryption_version` supports future key/algorithm rotation;
- migration creates storage columns only and does not implement cryptography.

## Timestamp/timezone contract

Use `TIMESTAMPTZ` for all instants:

```text
created_at
updated_at
last_verified_at
last_card_list_at
expires_at
ended_at
executed_at
sent_at
failed_at
```

Rules:

- application datetimes are timezone-aware;
- instants are stored as UTC instants;
- `created_at` and initial `updated_at` use server `now()` default;
- application code updates `updated_at` on every row update;
- no naive datetime is used in persistence contracts.

Use `DATE` for Kaiten calendar due dates when the Kaiten API value has no explicit time component.

Notification classification is computed relative to:

```text
notification_settings.timezone
```

It must not depend on the database, OS, or server process timezone.

## Notification dedup/delivery contract

Notification event types:

```text
DUE_SOON
DUE_TODAY
OVERDUE
```

Delivery states:

```text
RESERVED
SENT
FAILED
```

Dedup key:

```text
user_id
kaiten_card_id
due_date
notification_type
```

`due_date` is required in the key so a changed Kaiten deadline creates a distinct notification event.

Minimal reservation workflow:

1. Worker calculates candidate event from live Kaiten data.
2. Worker attempts insert into `notification_history` with `delivery_status = 'RESERVED'`.
3. If the insert conflicts on `uq_notification_history_dedup`, the event is a duplicate and is skipped.
4. If reservation succeeds, send MAX notification.
5. On success, update to `SENT` and set `sent_at`.
6. On failure, update to `FAILED`, set `failed_at`, and store safe `error_type`.

This is not a full outbox. A retry policy for `FAILED` rows is outside the first migration unless separately requested.

## Transaction boundaries

| Operation | Atomic database work |
|---|---|
| MAX binding | create/find `users`; create/update `max_chats`; create default `notification_settings` if required |
| Kaiten binding | encrypt token outside DB; insert/update `kaiten_connections`; update status and verification metadata |
| Dialog update | find/create active dialog; lock active session; update dialog context |
| Pending command creation | insert `pending_commands`; update dialog context in the same transaction |
| Clarification handling | lock active pending command; verify current state; update resolver state/candidates; update dialog context |
| Command completion | after external Kaiten result, update pending command state, timestamps, failure reason, and context |
| Notification send | attempt `RESERVED` insert; on conflict skip; send MAX; update `SENT` or `FAILED` |

External Kaiten/MAX calls are not executed by the database. Transaction scopes must be chosen so DB state does not claim a Kaiten mutation succeeded before the actual result is known.

## Concurrency invariants

| Invariant | Enforcement |
|---|---|
| One active dialog session per user | partial UNIQUE `uq_dialog_sessions_one_active_per_user` |
| One active pending command per dialog session | partial UNIQUE `uq_pending_commands_one_active_per_session` |
| One notification reservation per dedup key | UNIQUE `uq_notification_history_dedup` |
| Clarification reply cannot mutate terminal command | row-level lock plus application/repository state check |
| Duplicate webhook message must not create conflicting active state | transaction plus active-session and active-command constraints |
| Pending command owner equals dialog session owner | application/repository invariant and tests |
| JSONB payloads do not replace stable relational data | schema design plus repository contract |

No distributed locking infrastructure is part of MVP.

## Pending command ownership invariant

`pending_commands` stores both:

```text
user_id
dialog_session_id
```

This is intentional denormalization for:

- user-scoped queries;
- tenant isolation checks;
- recovery/debug operations;
- simpler repository method signatures.

Required invariant:

```text
pending_commands.user_id == dialog_sessions.user_id
where pending_commands.dialog_session_id = dialog_sessions.id
```

First migration must not add a composite FK solely for this invariant. `002-01` must enforce it through:

- repository/application creation flow;
- transaction that loads/locks the dialog session before inserting the pending command;
- tests that reject mismatched `user_id` and `dialog_session_id`.

## Retention and cleanup classification

Persistent until explicit product decision:

```text
users
max_chats
kaiten_connections
notification_settings
notification_history
```

TTL-managed or cleanup-eligible later:

```text
dialog_sessions
pending_commands
previous_user_message
previous_bot_message
last_card_list
pending command candidates
pending command unresolved_entity
pending command arguments
```

Cleanup rules for future implementation:

- ended or expired `dialog_sessions` may be deleted after retention TTL;
- terminal `pending_commands` may be deleted after retention TTL;
- stale active `pending_commands` should transition to `EXPIRED` before deletion;
- `last_card_list` and previous messages are overwritten during normal dialog handling;
- no `deleted_at` or `is_deleted` fields are added in MVP.
